# Outcast Hearing

> Source: OutcastHearing/README.md (compiled 2026-08-10, verified against Project Zomboid 42.20). Imported 2026-09-29. Confidence tags in the text are the original author's.

Gunfire damages your hearing. Ear protection prevents it, quiet recovers it, and
enough of it is permanent. Project Zomboid **B42 only**.

**Mod id:** `OutcastHearing` | **Author:** Raxdeg / Dystopian Outcasts
**Requires:** nothing. **No dependencies at all** -- not OutcastLib, not
MoodleFramework, not a UI library.

> **Status: the readout is implemented and unit-tested, and this is packaged as a
> Workshop test build for a dedicated multiplayer server. Nothing has been
> confirmed in game yet.**
>
> Shipping the generic readout -- `OH_Readout` (model), `OH_ReadoutHUD` (element),
> `OH_ReadoutController` (driver) -- with **70 checks green** under
> `lua test_all.lua`, a Mod Options panel, and a throwaway `OH_Probe` that feeds
> it fake values on four numpad keys.
>
> **The hearing simulation is not written.** The readout is deliberately first:
> it is the part the design is least sure of, it is generic so it outlives this
> mod, and building it first means the simulation can be watched rather than
> inferred from a console log.

## Proving the readout in game

Enable **Outcast Hearing** (no other mod is required), load any save, and use the
numpad:

| Key | Does | Watch for |
|---|---|---|
| `Numpad 1` | damage -- value down ~8.5%, re-arms the dwell | panel fades IN; bar shrinks; delta reads red; two contributor lines |
| `Numpad 2` | recover -- value up ~4%, capped at the floor | delta reads green; bar cannot pass the yellow tick |
| `Numpad 3` | permanent -- floor down 6%, **silent** | yellow tick moves left; **panel must NOT reappear if faded** |
| `Numpad 0` | reset to pristine, and add a second row | two rows; row 2 uses a `0.42` formatter and has no tick |

**Numpad, not F-keys, and that was a real bug.** The first cut used F9-F12;
`keyBinding.lua:191` binds F10 to *Take screenshot* and `:357` binds F11 to
*Toggle Lua Debugger*. The probe would have spammed screenshots and toggled the
Lua debugger on a live server. Vanilla binds nothing on the numpad.

`Numpad 3` is the interesting one: it pushes with `delta = nil`, which is the
path a server resync takes in the simulation. If the readout is faded out, the
tick must move without the panel coming back. That behaviour is unit-tested;
this is where it gets confirmed by eye.

Then stop pressing keys: after `dwellMs` (5s) the delta text should disappear
while the bar keeps its value, and the panel should fade out over `fadeMs`
(400ms) and remove itself.

**Change Options > Display > UI scaling and press the keys again.** The row
metrics are hardcoded pixels and this is the assumption most likely to be wrong.

The probe prints its state to the console on every press, so the numbers on
screen can be checked against the numbers in the log.

The design and the research behind it are in our Build 42 trait notes --
`05-p0-hearing-design.md` for this mod, `03-b42-trait-api.md` for the engine
facts, `01-b42-trait-reference.md` for the trait data.

## Why this mod exists

Evolving Traits World already makes ~60 vanilla traits dynamic, so a general
"traits you earn" mod would be re-treading tested work. The measured gap
(`_dev/B42_Traits/04-p0-candidates.md`) is narrower and more interesting:

- **The signal is the player's own optimal play.** Guns are loud and effective;
  the drawback is generated by using them well.
- **The counterplay is already in vanilla.** `Hat_EarMuffs` carries
  `HearingModifier = 0.75`, `Hat_EarMuff_Protectors` is dedicated protection, and
  both occupy the hat slot -- so protection is a real trade.
- **It is orthogonal to ETW.** ETW drives `hardofhearing`/`keenhearing` off
  sneaking/lightfooted/sprinting *skill* (`ETW_BySkills.lua:160-185`). Noise
  exposure is a different signal on the same three traits.
- **`deaf` is untouched by every trait mod surveyed**, and at -12 it is the
  joint-largest negative in the game.

## Standalone, on purpose

The first cut of this mod declared `require=OutcastLib`. That was removed, and
the reasoning is worth keeping because it applies to every gameplay mod in the
family:

1. **Wrong domain.** OutcastLib is a container- and world-scanning library --
   `OL_Containers`, `OL_Reach`, `OL_Squares`. This mod uses **none** of them. It
   touched only two generic utilities (an options getter and a gated logger)
   which happen to live there rather than belonging there.
2. **Wrong distribution.** OutcastLib is published on the Workshop (item
   `3778987608`) as an **unlisted** item, so it does not show in Workshop search.
   This is a gameplay mod. A hard `require=` on an unlisted library ties a public
   mod to a dependency players cannot find by searching, and upload time is an
   expensive place to discover that.
3. **The cost was real and the benefit was ~50 lines.** A dependency means the
   library must be installed, adds a version floor to maintain, and adds one more
   thing that breaks on a B42 point release.

The honest cost: `OH_Support.lua` is a **fourth** copy of an options getter that
OutcastLib partly exists to de-duplicate (`OP_Options.lua:39`,
`ORA_Options.lua:43`, `OSA_Options.lua:33` were byte-identical). That is a real
loss, recorded rather than glossed. The trade is accepted because those three are
container mods inside one private server's mod set, and this is neither. The
contracts in `OH_Support` are deliberately identical to the library's, so if this
mod ever takes a dependency for a *good* reason, it is a swap and not a rewrite.

A knock-on benefit: the test suite now needs no `pz_stub` and no sibling repo on
the path. `OH_Readout` is pure Lua, so 70 checks run against nothing but a Lua
interpreter.

## No moodles

The readout is a custom HUD element, not a moodle. Moodles exist to avoid telling
the player the number; this server's convention is the opposite -- real bars,
real numbers, on screen when they matter and gone when they do not.

The practical consequences are good ones:

- **No MoodleFramework dependency.** `ISPanel`, `UITransition` and
  `ISUIElement:drawProgressBar` are all base game, so there is one less required
  mod in the server's load order and one less thing to break on a point release.
- **"Pin it open" is one branch.** Under MoodleFramework it is a fight:
  `MF.ISMoodle:setValue` auto-removes a moodle whenever it sits in the neutral
  band.
- **The permanent-damage floor is drawable.** It is a second mark on the same
  track. A moodle has one level and cannot show it at all.

## The two-pool model

Hearing is one scalar in `0..1`, split:

| Pool | Behaviour |
|---|---|
| `value` | what the character hears with now. Falls with exposure, recovers toward `floor` with quiet. |
| `floor` | the ceiling `value` can recover to. Only ever falls, and only when loss is held deep for a sustained period. |

Real audiology calls the recoverable part a temporary threshold shift. The split
is the whole reason the readout is worth looking at: it separates "rest and this
comes back" from "this is gone".

Trait thresholds sit on `value` -- `keenhearing` / none / `hardofhearing` /
`deaf`. All three carry no `XPBoosts`, which is why they are safe to cycle:
`getCharacterTraits():remove()` does **not** claw back perk boosts, so a boosting
trait would ratchet. They are also a closed mutual-exclusivity cluster of exactly
three, so stripping the other two on a transition is complete by construction.

## The readout is generic on purpose

`OH_Readout` and `OH_ReadoutHUD` know nothing about hearing. They are a registry
of named stats -- value, optional permanent floor, the delta that last moved it,
and the reasons why -- plus the dwell bookkeeping that decides visibility.

**Generic in shape, but owned by this mod.** They are not shared through a
library, and they should not be until there is something to share them *with*.
The three files -- model, element, driver -- are written so a sibling dynamic-
trait mod can lift them wholesale: `OH_Readout.lua` is pure Lua with no engine
calls (the caller injects `nowMs`), so rebinding the name is the entire port.

Do that when a **second** dynamic-trait mod exists and the two copies would
otherwise drift. Copying once at that point costs an afternoon; a dependency
taken early costs a version floor and a load-order coupling forever -- and if the
shared thing lives in a private library, it costs the ability to publish at all.

### Model / element split

The model owns every decision; the element owns only drawing. That is what makes
60 headless checks possible against a UI feature -- `ISPanel` and `UITransition`
need the real engine, but "should this be on screen", "in what order", "is this
delta stale" do not.

```
Readout.define(id, spec)                    declare once at load
Readout.update(id, nowMs, state)            push new state; a nil delta is silent
Readout.clearDelta(id)                      dwell expired, keep the value
Readout.rows()                              what to draw, ordered, stable
Readout.shouldShow(nowMs, dwellMs, pinned)  should the element be up
Readout.msUntilHidden(...)                  for logs and assertions
```

Two behaviours worth knowing at the call site:

- **A silent update does not re-arm the dwell.** `update` with no `delta`
  corrects the number without making a faded-out readout jump back on screen --
  which is what a server resync must do.
- **A stat that has never reported is not drawn.** Not drawn at 0%. Rule 4
  applied to a display: a plausible-looking zero where the honest answer is "no
  data".

## Engine facts this depends on

Verified against the installed build **42.20.0**, revision `a2947723ca`, and the
sealed decompile of that build.

**`UITransition.setFadeIn()` ignores your fade duration.** It hardcodes
`init(100, false)` in and `init(200, true)` out (`UITransition.java:59-67`). It is
the obvious API and it is the wrong one for a configurable dwell -- use
`init(durationMs, fadeOut)` directly.

**`UITransition.init` handles mid-transition reversal.** If the direction flips it
seeds `elapsed` from the current fraction (`:29-40`), so a readout that has
started fading and is re-armed resumes from where it is instead of snapping. That
is why `show()`/`hide()` are safe to call repeatedly.

**`UITransition.update` snaps to the end if the element stopped updating.** When
`ignoreUpdateTime` is false and the gap exceeds the duration, `elapsed` jumps to
`duration` (`:43-48`). Call `setIgnoreUpdateTime(true)`, as `ISChat` does.

**`fraction()` is direction-corrected** (`:55`) -- it returns `1-frac` when fading
out, so it always runs 0 (invisible) to 1 (opaque). Multiply it into every alpha.

**Trait mutation grants none of its side effects.** `getCharacterTraits():add()`
skips `GrantedRecipes`, `XPBoosts` and `GrantedTraits`, and does not enforce
`MutuallyExclusiveTraits` -- the engine only checks exclusivity at character
creation. `remove()` does not claw XP boosts back. Full detail and working
replay code in `_dev/B42_Traits/03-b42-trait-api.md`.

**`item:getHearingModifier()` is callable from Lua.** Confirmed empirically -- the
shipping mod *Better Clothing Info Comparison* calls it and sums it across
`getWornItems()` (`3036830549/.../bcic_TooltipClothing.lua:26,104`).

**Firearms carry `SoundRadius`** in `media/scripts/generated/items/weapon.txt`,
30 (cap gun) to 200 (shotgun) across 22 vanilla guns. Use it as the damage scalar
so modded guns get sensible values for free.

**There are no suppressors in vanilla B42** -- `weaponpart.txt` has no
Suppressor/Silencer item.

**Never write a UTF-8 BOM.** PowerShell 5.1's `Set-Content -Encoding utf8`,
`Out-File` and `Export-Csv -Encoding utf8` all emit one, and a BOM silently voids
an entire PZ script file.

## Layout

```
OutcastHearing/
  Contents/mods/OutcastHearing/42/
    mod.info                    id=OutcastHearing  no require=  versionMin=42.20.0
    media/lua/shared/OutcastHearing/
      OH_Config.lua             identity, thresholds, Mod Options defaults
      OH_Support.lua            options getter + console logger; why there is no library
      OH_Log.lua                joins the shared Outcast.log when OutcastLib is present
      OH_Readout.lua            GENERIC stat model -- pure Lua, no engine calls
    media/lua/client/OutcastHearing/
      OH_Probe.lua              THROWAWAY bench instrument -- delete when the simulation lands
      OH_ReadoutController.lua  GENERIC driver -- mounts, ticks, holds no policy
      OH_ReadoutHUD.lua         GENERIC element -- ISPanel + UITransition

  scripts/install-junctions.ps1 vendored byte-identical from _shared/
  tests/harness.lua             stub load, require shim, assertions
  tests/test_all.lua            runs every suite; exits non-zero on failure
  tests/test_readout.lua        70 checks over the model
  README.md
```

`OH_ReadoutController` requires `OH_ReadoutHUD` explicitly, and that require is
**load-bearing**: PZ loads a directory alphabetically and `...Controller` sorts
before `...HUD`, so the global does not exist yet at that point in load. It would
have worked by accident, because `mount()` runs later at `OnCreatePlayer` -- but
that leaves the file one rename away from breaking.

`OH_Config` and `OH_Readout` ship under `shared/` so the headless tests can
require them and both Lua states see them. The element is `client/` because
nothing on a server draws.

## Build and test

No build step -- PZ loads Lua directly.

```powershell
.\scripts\install-junctions.ps1     # junction into ~/Zomboid/mods + /Workshop

cd tests                           # paths in the suite are relative to here
lua test_all.lua                   # headless, no game needed
```

There is no `pz_stub.lua` and nothing on the path but this repo. `OH_Readout`
touches no engine type, so the suite runs against a bare Lua interpreter -- which
is the payoff of keeping every decision in the model and none in the element.

## Logging -- read this before reporting "it doesn't work"

Everything lands in **`Zomboid/Lua/Outcast.log`**, the single file every Outcast
mod shares, whenever `OutcastLib` is installed. If it is not, the same lines go
to the console instead and the mod is otherwise unaffected.

Look for one **ungated** boot line per session:

```
[OutcastHearing] loaded | host: dedicated server | file log: Outcast.log (via OutcastLib) | logging at load: OFF ... | readout: on | test keys: on (Numpad 1/2/3/0)
```

Plus an ungated line saying whether the readout mounted, and one per probe key
press. Those three are ungated deliberately: after a session where nothing
appeared on screen, **"did not load", "chose not to mount" and "mounted and
nothing happened" have to be three distinguishable outcomes**, and that must not
depend on having thought to switch logging on beforehand.

`OutcastProximity` hit this exact dead end first -- a session logged with debug
off came back with a log containing nothing but its own header, which is
indistinguishable from a mod that failed to load. The line that would have
explained it was itself behind the gate.

### OutcastLib is a soft dependency, here and only here

There is no `require=OutcastLib` in `mod.info` and there will not be -- the
reasoning above still stands. But `Outcast.log` is **not** a utility that can be
copied. It is one file behind one buffer with one truncate flag, and
`OutcastLib.Debug.setFile` says so outright: several mods calling it with the
same name is the *expected* case, and reopening "clears the buffer and re-arms
the truncate, so the second mod to ask would discard whatever the first had
buffered and then overwrite the file".

A second independent sink writing `Outcast.log` would not be duplication, it
would be **silent corruption of the shared log**. That is a real distinction from
the options getter: copying a pure utility costs a fourth copy; copying shared
mutable state costs the shared state.

So the library's sink is used when present and skipped when absent, and the
detection happens at `OnGameStart`/`OnServerStarted` rather than file scope --
without `require=` the load order is not guaranteed, but by boot every mod has
loaded.

## Multiplayer

**What this test build can prove:** that the mod loads on a dedicated server
without erroring, that clients can join with it enabled, that `OnCreatePlayer`
and `OnTick` fire the same way they do in singleplayer, and that the element
renders and fades correctly on a real client. That is worth knowing before the
simulation is written on top of it.

**What it cannot prove:** anything about the simulation, which does not exist.
The probe's numbers are **client-local, not authoritative, and not synced** --
each client drives its own. Two players pressing Numpad 1 will see different
values, and that is correct for what this is.

### Why it is server-safe

Everything that touches the engine is under `client/`, so a dedicated server
never loads it:

| File | State | Touches |
|---|---|---|
| `shared/OH_Config.lua` | both | nothing -- plain data |
| `shared/OH_Support.lua` | both | `PZAPI`, behind a `type(PZAPI) ~= "table"` guard |
| `shared/OH_Log.lua` | both | `Events.OnGameStart` **and** `Events.OnServerStarted` |
| `shared/OH_Readout.lua` | both | nothing -- pure Lua |
| `client/OH_Options.lua` | client | `PZAPI.ModOptions` |
| `client/OH_ReadoutHUD.lua` | client | `ISPanel`, `UITransition` |
| `client/OH_ReadoutController.lua` | client | `Events`, `getTimestampMs` |
| `client/OH_Probe.lua` | client | `Events`, `Keyboard`, `getPlayer` |

The shared files were audited for engine calls specifically because they load in
the server Lua state. `OH_Support` degrades to `OH.DEFAULTS` when `PZAPI` is
absent rather than raising, and `OH_Log` registers **both** lifecycle events:

> `OnGameStart` is raised only from `IngameState.java:768`, which a dedicated
> server never enters. `OnServerStarted` (`GameServer.java:1522`) is its
> server-side counterpart and fires nowhere else. Registering only the first
> means a dedicated server writes **no boot line at all** -- the log an operator
> goes looking for after a failed session is simply absent. Vanilla pairs them
> the same way at `CustomTileProps.lua:341-342`.

**No network commands are sent or received.** When the simulation lands that
changes -- detection and the authoritative scalar move to `media/lua/server/`,
with the client rendering what it is told.

### Deploying to the test server

1. Upload from the in-game Workshop uploader (the junction at
   `%USERPROFILE%\Zomboid\Workshop\OutcastHearing` already points here).
2. Put the assigned id into `workshop.txt` -- `id=` is deliberately blank until
   the first upload assigns one.
3. Server ini: add the id to `WorkshopItems=` and `OutcastHearing` to `Mods=`.
4. `versionMin=42.20.0` -- if the test server runs an older build the mod is
   marked unavailable and silently drops off the list.

## Not done yet

**The simulation.** `OnPlayerAttackFinished` + `weapon:isRanged()`, damage scaled
by `SoundRadius`, enclosure multiplier via `character:isOutside()`, mitigation via
summed `getHearingModifier()`, recovery on a timer, and the permanent floor.
Server-authoritative, with the client rendering what it is told.

**The trait transitions.** Threshold crossings applying and stripping the
three-trait cluster through a side-effect-safe add/remove path.

**The character-info tab.** The always-available full picture for when the
readout has faded. ETW's `CharacterInfoAddTab.lua` is a 40-line precedent.

**Unverified, and what the probe is for:**

- That the element renders at all -- no line of `OH_ReadoutHUD` has executed.
- Whether `PANEL_W = 240` and the row metrics are right at non-default UI scales.
- Whether the fixed screen anchor collides with anything on the server's HUD.
- Whether the readout renders correctly on a **dedicated server** client, and
  whether `OnCreatePlayer` fires the same way there as in singleplayer. That is
  the specific reason this is packaged for Workshop now.

## Open questions

1. **ETW precedence.** ETW writes the same three traits from a different signal.
   Detect and yield, detect and suppress its hearing channel, or ship standalone
   and document it? Needs deciding before release, not before the simulation.
2. Should `keenhearing` be earnable at all, or should pristine simply mean "no
   trait"? Granting a positive trait for never firing a gun may reward passivity.
3. Does deafness need a survivability floor in MP, or is `deaf` at -12 accepted
   as intended harshness?
